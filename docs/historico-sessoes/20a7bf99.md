## O Rich Players vai correr com os 300 min? Sim. O que lhe fiz e porquê

**O problema (porque estava cancelado 3 semanas seguidas):**

O scrape tem 3 fases. A **Fase 2** (dados ricos por torneio — para cada torneio, buscar metadados + tee-times paginados de milhares de torneios) é lentíssima e **não cabe no limite de 6h** do GitHub Actions para todo o backlog acumulado.

O detalhe crítico: no workflow, o **step de commit só corria DEPOIS do scrape terminar**. Como o scrape nunca terminava em 6h, o GitHub **cancelava o job a meio da Fase 2** — e aí não se committava **nada**, nem sequer a *cache aquecida* (os torneios que já tinham sido processados). Resultado: na semana seguinte recomeçava **do zero, a frio**, e voltava a ser cancelado. Um ciclo perpétuo.

**O que fiz — um "orçamento de tempo" (`--max-runtime-min 300`):**

1. Adicionei o parâmetro `--max-runtime-min` ao script. O workflow passa **300** (5h).
2. Ao arrancar, o script calcula um **prazo**: `agora + 300 min`.
3. As duas fases lentas (Fase 1 = carreiras, Fase 2 = dados por torneio) verificam o prazo no início de cada iteração. Quando o prazo é atingido, **param graciosamente**: gravam a cache aquecida no disco e escrevem os ficheiros de jogador já feitos.
4. O script **sai com exit 0/2 (nunca cancelado)** → o step de commit **corre** e persiste o progresso (cache + ficheiros).

**Porque é que isto resolve, mesmo não terminando numa só corrida:**

- A **cache de torneios** (`uskids-rich-flight-cache.json`) fica committada **aquecida**. Na corrida seguinte, os torneios já em cache são *cache hits* → a Fase 2 fica muito mais rápida.
- O `--since-days 14` faz cada corrida saltar os jogadores já processados nos últimos 14 dias → continua nos que faltam.
- Ao fim de ~2-3 corridas semanais a cache está quente o suficiente para **completar tudo**; depois entra em regime incremental rápido.
- Os 300 min deixam ~60 min de folga sob o limite de 360 min para o `npm ci` + commit + push.

Também mudei o step de commit para correr em **exit 2** (além do 0), porque a cache aquecida deve persistir mesmo numa corrida em que nenhum ficheiro de *jogador* mudou (o `git diff --cached --quiet` no-opa se realmente nada mudou).
