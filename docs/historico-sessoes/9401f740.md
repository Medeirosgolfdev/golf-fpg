Encontrei a causa. É um bug de fuso horário no pipeline — e é grande: **120 das 187 voltas deste jogador têm o dia errado (−1 dia)**. Não é só a Quinta do Peru.

## O que se passa

1. A FPG devolve a data de cada volta em dois formatos: string (`hcp_dateStr: "2026-06-28"` — **correcta**) e epoch .NET (`hcp_date: /Date(1782601200000)/`). O epoch codifica a **meia-noite em hora de Lisboa/Madeira**, que no horário de verão (UTC+1) corresponde a **23:00 UTC do dia anterior**.

2. O pipeline ignora a string e usa o epoch: [helpers.js:242](lib/helpers.js:242) (`getPlayedAt` → `parseDotNetDate(hcp_date)`) e depois [helpers.js:25](lib/helpers.js:25) (`fmtDate` formata com `getDate()`/`getMonth()` — **hora local da máquina**).

3. No teu PC (Madeira, UTC+1 no verão) isto dava certo. Mas o `data.json` agora é gerado pelo GitHub Actions (`update-data.yml`), que corre em **UTC** — e aí `2026-06-27T23:00:00Z` formata como **27-06** em vez de 28-06.

Por isso o padrão dos 120 erros: **todas as voltas jogadas no horário de verão português** (fim de Março a fim de Outubro) ficam com −1 dia; as de inverno (UTC+0, epoch = meia-noite UTC) ficam certas. Isto afecta os `data.json` de **todos os jogadores** regenerados pelo Actions, não só o 49124. O agrupamento por dia também usa o epoch (`Math.floor(dateSort / MS_PER_DAY)` em [process-data.js:655](lib/process-data.js:655)), por isso voltas de verão caem no balde do dia anterior.

## Correcção que proponho

Deixar de depender do fuso da máquina: em `getPlayedAt`, preferir a **string** `hcp_dateStr`/`score_dateStr` (parse manual `YYYY-MM-DD` → Date em UTC-meia-noite) e só cair no epoch quando a string não existir — e nesse caso normalizar o epoch para o dia civil de Lisboa (somar 1h antes de truncar, ou formatar com `Intl.DateTimeFormat` em `Europe/Lisbon`). Depois é preciso **regenerar os `data.json` de todos os jogadores** (`node pipeline.js --all --skip-import` ou esperar pelo próximo run com `full_rebuild`), porque as datas erradas já estão gravadas nos ficheiros committed.

## A correcção

- [helpers.js](lib/helpers.js) — `getPlayedAt` agora prefere as **strings de data** da FPG (`hcp_dateStr`/`score_dateStr`, sempre exactas); os fallbacks de epoch passam por `lisbonCivilDay()` (converte para o dia civil de Lisboa via `Intl`); `fmtDate` passou a getters UTC. Resultado independente do fuso da máquina.
- [process-data.js](lib/process-data.js) — datas de treinos e extra_rounds construídas em UTC para ficarem consistentes.

**Verificação:** regenerei o jogador 49124 com `TZ=UTC` (a simular o Actions) — **0 datas erradas em 187** (antes: 120), Quinta do Peru D2 agora sai `28-06-2026`; testei os helpers em `TZ=America/New_York` (dá sempre o dia certo, verão e inverno); `npm test` 217 passed, `npm run build` OK.
